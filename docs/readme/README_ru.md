# dsh-pi-bridge

Один плагин, два хоста. Установленный в pi, он даёт pi использовать плагины DeepSeek Harness; установленный в DSH — даёт DSH использовать плагины pi. Ни одна из сторон не «переводит» чужой код, чтобы исполнить его: плагин всегда выполняется в его собственном хосте — там API хоста настоящая — а вторая сторона лишь передаёт вызовы.

```text
# pi
pi install npm:dsh-pi-bridge            # либо: pi install git:github.com/Twofruitsgrape/dsh-pi-bridge

# DSH
dsh plugin --profile <name> install github:Twofruitsgrape/dsh-pi-bridge
```

После установки перезапустите хост. Оба ключевых слова (`pi-package` и `dsh-plugin`) объявлены, поэтому маркетплейс каждой экосистемы находит этот пакет.

## Что вы получаете в каждом хосте

| | pi | DSH |
|---|---|---|
| Использовать плагины другой стороны | `dsh_install`, `dsh_preview`, `/dsh-install`, `/dsh-preview` | `pi_install`, `pi_preview` |
| Управлять переброшенным | `/bridge-list`, `/bridge-remove` | `bridge_list`, `bridge_remove`, `bridge_status` |
| Скилл | `skills/dsh-pi-bridge/SKILL.md` | та же `SKILL.md`, смонтированная через реестр скиллов |

Обе стороны используют одну и ту же грамматику источников: `npm:<pkg>[@ver]`, `git:github.com/<owner>/<repo>[@ref]`, `github:<owner>/<repo>`, URL репозитория или локальный путь — ровно те форматы, которые каждый хост и так принимает.

Фрагмент реальной сессии, дословно: настоящий запуск DSH, настоящая модель, установка реально опубликованного пакета pi.

```text
dsh> pi_install({ source: "npm:pi-web-access", prefix: "web" })
  bridged npm:pi-web-access as pi-web-access@0.41.0
    mode: package code runs natively inside a supervised pi process
    tools: web_web_search, web_source_check, web_fetch_content,
           web_get_search_content, web_web_enable
    pi slash commands registered in pi: /websearch, /curator, /google-account, /search

dsh> web_web_search({ query: "DeepSeek V4" })   # инструмент, пришедший из пакета pi
  -> живые результаты поиска, полученные самим провайдером пакета с его настройками
```

## Как это работает

### Плагины pi внутри DSH: поднадзорный процесс pi

`pi_install` овеществляет пакет в кэш моста, устанавливает его настоящие зависимости, а затем загружает его в поднадзорном мосту процессе pi (`pi --mode rpc`). Каждый пункт, о котором отчитался pi, становится инструментом в DSH; вызовы пересылаются к pi и возвращают результат, вычисленный pi. Каталог `SKILL.md` монтируется как данные через `ctx.skills`. Пакет видит настоящий `registerTool` pi, его `registerProvider`, реестр моделей и учётные данные провайдеров — пакет, работающий с сетью или моделями, ведёт себя в точности как в руках пользователя pi.

Этот дизайн сменил прежний подход: реплицировать регистрации в DSH и полагаться на import-заглушки. Тот вариант успешно проходил все mock-тесты и разваливался перед настоящими пакетами — потому что import-заглушка это инструмент, который не работает. Пересылка в родной хост — единственная форма, которая может оставаться честной к результатам.

### Плагины DSH внутри pi: живая сессия DSH

Бандл DSH требует настоящий `ctx.tools`, настоящий `ctx.llm` и реестр скиллов, поэтому `dsh_install` просит живую сессию DSH самой загрузить бандл. Препятствие: бандл, установленный менеджером плагинов, — это симлинк под `node_modules` профиля, и оголённые спецификаторы `@deepseek-ai/*` не резолвятся — замер дал `MODULE_NOT_FOUND`. Именно это исправляет `src/dsh-loader.js`: он переписывает такие спецификаторы в URL модулей, которые несёт работающая сборка (настоящие пакеты, не заглушки); относительные импорты, `node:` и сторонние остаются как есть. Бандл регистрируется в хосте, а pi получает перенаправляемый инструмент на каждую capability.

Эндпоинт по умолчанию закрыт; обычный запуск DSH не открывает ни одного порта:

```bash
DSH_PI_BRIDGE_DSH_SERVE=43191 dsh ...                    # сторона DSH
DSH_PI_BRIDGE_DSH_ENDPOINT=127.0.0.1:43191 pi ...        # сторона pi
```

Привязка только к 127.0.0.1; клиент отвергает не-loopback-адреса. Когда живой DSH недостижим, `dsh_install` честно говорит об этом и отступает в режим перевода, а не притворяется, что пересылка удалась.

### Когда ни один хост недостижим

Мост всё равно разрешает источник, компилирует TypeScript (`stripTypeScriptTypes` из `node:module`, без скачивания тулчейна) и фиксирует, что пакет зарегистрировал бы, поэтому `preview` работает везде. Репликация регистраций в другой хост остаётся для сценариев в одном хосте и для бандлов, чей payload целиком данные — у бандла DSH, чистого каталога скиллов, нет вызываемого, но сам скилл проходит. Оба хоста реализуют [спецификацию Agent Skills](https://agentskills.io/specification).

### Формы параметров и результатов

Инструменты DSH несут таблицу свойств (`{ text: { type: "string", required: true } }`), которую `@deepseek-ai/dsh-tools` компилирует в JSON Schema; инструменты pi несут JSON Schema напрямую (TypeBox). `src/schema.js` конвертирует в обе стороны, и результаты проходят ту же проекцию: `{ content: [{ type: "text" }] }` pi и `{ ok, result }` DSH переводятся друг в друга. Хост валидирует схемы при регистрации, и принимаемое подмножество уже чернового JSON Schema — маркер `required` на узле свойства или объектный массив `required` в схеме результата валит активацию всего плагина. Эти правила взяты из замеров на установленных хостах; тестовый набор несёт их как ассерты.

## Проверено — и как

Каждый пункт ниже проверялся против настоящих хостов, а не против подставок:

- Настоящий запуск DSH, настоящая модель, установка `npm:pi-web-access` и вызов через него `web_web_search` (результаты добывает собственный провайдер пакета)
- Настоящая сессия DSH загружает бандл с оголённым импортом `@deepseek-ai/dsh-tools`, затем отдельный процесс вызывает его инструменты через loopback
- Этот мост исполняет собственный DSH-вход тем же механизмом, который чужой бандл встречает в pi

Каждый из них поймал баг, недоступный подставе: файл, забытый опубликованным манифестом; схему результата, которую хост отвергает и из-за которой плагин тихо бездействует; `process.execPath`, указывающий в процессе хоста на приложение, а не на node; ноль capabilities при переустановке, потому что демон уже загрузил пакет; scope, запрещающий присвоение свойств; server handler вне волокна, поднимающего сервис; хост, отвергающий дублирующиеся имена инструментов.

```bash
npm test                # все офлайн-наборы
npm run test:offline    # пайплайн + хост-входы обеих сторон
npm run test:proxy      # демон, пересылка на стороне DSH и на стороне pi
npm run test:host       # против установленной сборки DSH (см. примечание)
npm run test:network    # реально опубликованные пакеты из npm и GitHub
npm run test:live       # то же — против реально работающего pi
```

`test:host` читает собственный `@deepseek-ai/dsh-tools` хоста изнутри asar установленного хоста — это возможно только через fs с патчем Electron; запускайте его внутри процесса хоста. Под обычным node он прямо сообщает SKIP, не намекая, что хост нам отказал.

Офлайн-наборы собирают фикстуры руками — TypeScript-расширение pi на билдере TypeBox, бандл DSH на `defineTool`, бандл с оголённым импортом пакета хоста — и гоняют весь пайплайн против записанных подставок, а затем по-настоящему исполняют инструменты, вышедшие из моста. Некоторые правила живут статическими ассертами, потому что раскрываются лишь при настоящем старте: формы схем, принимаемые хостом; файлы, обязательные к публикации; то, что анализируемый бандл не должен поднимать процессы и занимать порты.

## Что не переходит

Мост честно сообщает о таких случаях, а не тихо проваливается:

- **UI хоста**: браузерные страницы DSH / `ctx.slots`; TUI-рендерер pi, `ctx.ui`, сочетания клавиш, флаги CLI.
- **Адаптеры моделей, зарегистрированные в хосте**: тот, кто добавляет провайдера, делает это против собственного хоста — в этом и смысл «не переводить» — провайдеры pi оседают в pi, адаптеры DSH — в DSH.
- **Бандлы DSH без вызываемого**: чистый оверлей интерфейса или настроек не имеет инструментов для пересылки. preview честно это констатирует, а не выдумывает возможности.
- **Пакеты, требующие интерактивного хоста**: пересланный вызов может стримить прогресс, но не может всплывающий выбор открыть на другой стороне.

## Постоянство

Регистрации немедленно падают в текущую сессию. Каждый хост при загрузке плагина перечитывает из `~/.dsh-pi-bridge/bridges.json` то, что сам записал, поэтому установка переживает перезапуск — проверено перезапуском сессии DSH с обнаружением инструментов моста на месте. Перечитывание читает только кэш: старт хоста никогда не ждёт сетевой загрузки; если кэш очищен, мост сообщает о недоступности, а не виснет. Перезапуск делает новые инструменты видимыми и другим клиентам (веб-GUI, второе окно), потому что они собирают список инструментов при старте. Отключается настройкой `restoreOnLoad: false` в конфигурации бандла.

Ни в настройки какого-либо хоста мы не пишем. `bridge_remove` забывает мост и стирает его каталог сборки; инструменты, уже зарегистрированные в живом процессе, остаются до перезапуска, потому что молчаливая дерегистрация состояния хоста хуже, чем оставить их видимыми.

## Безопасность

Мост-пакет **исполняет код с вашими правами, на той стороне, где он работает**. Любой хост расширений выставляет то же требование; этот пакет пришёл из другой экосистемы и её маркетплейсовой ревизии не проходил, поэтому требование тем более. Сначала прочтите его исходный код; `preview` только разбирает и осматривает, ничего не регистрируя.

Пересылка — не песочница: пакет работает с полным доверием собственного хоста, потому это и работает. Loopback-эндпоинт привязывается только к 127.0.0.1, открывается лишь при заданном `DSH_PI_BRIDGE_DSH_SERVE`, а клиент отвергает не-loopback-адреса. Тот, кто дотянется до порта, сможет вызвать любой инструмент, загруженный сессией. Открывайте порт только когда нужно.

## Укладка

```text
index.js                вход DSH: name / inject / apply(ctx), то есть инструменты pi_*
extensions/index.js     вход pi: фабрика default(pi), инструменты и команды dsh_*
skills/dsh-pi-bridge/   SKILL.md, общий для обоих хостов
cordis.patch.yml        монтирование бандла DSH (цель тумблера в панели плагинов)
daemon/run.mjs          поднадзорный процесс pi; loopback-фасад его инструментов
daemon/bootstrap.js     загружается настоящим загрузчиком расширений pi внутрь pi
src/proxy.js            сторона DSH: запустить/переиспользовать демона, пересылать вызовы
src/dsh-loader.js       сторона DSH: загружать бандл в рантайме против живого scope
src/serve.js            сторона DSH: loopback-эндпоинт для другого хоста
src/dsh-host-client.js  сторона pi: говорить с живой сессией DSH
src/resolve.js          источники npm / git / url / локальные в кэш, с установкой зависимостей
src/load.js             построение зеркального дерева, компиляция TS, установка настоящих зависимостей
src/manifest.js         распознавание хоста по keywords, манифесту и форме каталога
src/capture.js          записанные подставки-хосты для обеих входных конвенций
src/schema.js           двустороннее преобразование схем параметров
src/capabilities.js     нормализованная модель capability; проекция результатов
src/replay-dsh.js       capabilities -> ctx.tools / commands / skills
src/replay-pi.js        capabilities -> pi.registerTool / registerCommand
src/restore.js          перечитывание записанных мостов при старте хоста
src/stubs.js            скан импортов и генерация заглушек для preview
src/tar.js              читатель gzipped-tar, без зависимостей
src/transpile.js        TypeScript -> ESM, через node:module
```

`index.js` импортирует только встроенное `node:` плюс собственный пакет и объявляет `inject: ["tools"]` — единственный нужный ему сервис. Скиллы и настройки достижимы через `ctx.inject` после проверки capability; профиль без реестра скиллов просто не монтирует скилл, вместо того чтобы падать на старте.
