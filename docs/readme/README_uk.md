# dsh-pi-bridge

Один плагін, два хости. Встановлений у pi, дає pi змогу користуватися плагінами DeepSeek Harness; встановлений у DSH — дає DSH користуватися плагінами pi. Жодна зі сторін не «переводить» чужий код, щоб його виконати: плагін завжди працює в його рідному хості — там API хоста справжня — а друга сторона лише переправляє виклики.

```text
# pi
pi install npm:dsh-pi-bridge            # або: pi install git:github.com/Twofruitsgrape/dsh-pi-bridge

# DSH
dsh plugin --profile <name> install github:Twofruitsgrape/dsh-pi-bridge
```

Після встановлення перезапустіть хост. Обидва ключові слова (`pi-package` та `dsh-plugin`) оголошені, тож маркетплейс кожної екосистеми знаходить цей пакет.

## Що ви отримуєте в кожному хості

| | pi | DSH |
|---|---|---|
| Використовувати плагіни іншої сторони | `dsh_install`, `dsh_preview`, `/dsh-install`, `/dsh-preview` | `pi_install`, `pi_preview` |
| Правити переброшеним | `/bridge-list`, `/bridge-remove` | `bridge_list`, `bridge_remove`, `bridge_status` |
| Скіл | `skills/dsh-pi-bridge/SKILL.md` | той самий `SKILL.md`, змонтований через реєстр скілів |

Обидві сторони вживають одну й ту саму граматику джерел: `npm:<pkg>[@ver]`, `git:github.com/<owner>/<repo>[@ref]`, `github:<owner>/<repo>`, URL репозиторію або локальний шлях — саме ті формати, які кожен хост і так приймає.

Шматок реальної сесії, дослівно: справжній запуск DSH, справжня модель, встановлення реально опублікованого пакета pi.

```text
dsh> pi_install({ source: "npm:pi-web-access", prefix: "web" })
  bridged npm:pi-web-access as pi-web-access@0.41.0
    mode: package code runs natively inside a supervised pi process
    tools: web_web_search, web_source_check, web_fetch_content,
           web_get_search_content, web_web_enable
    pi slash commands registered in pi: /websearch, /curator, /google-account, /search

dsh> web_web_search({ query: "DeepSeek V4" })   # інструмент, який прийшов із пакета pi
  -> живі результати пошуку, здобуті самим провайдером пакета з його налаштуваннями
```

## Як це працює

### Плагіни pi входять у DSH: піднаглядний процес pi

`pi_install` пересаджує пакет у кеш моста, встановлює його справжні залежності, а далі завантажує його в піднаглядному мостом процесі pi (`pi --mode rpc`). Кожен пункт, про який відзвітував pi, стає інструментом у DSH; виклики переправляються pi й повертають результат, обчислений pi. Теку `SKILL.md` змонтовано як дані через `ctx.skills`. Пакет бачить справжній `registerTool` pi, його `registerProvider`, реєстр моделей і облікові дані провайдерів — пакет, що торкається мережі чи моделей, поводиться точнісінько як у руках користувача pi.

Цей дизайн замінив колишній підхід: реплікувати реєстрації в DSH і покладатися на імпорти-заглушки. Той варіант успішно минав усі підставні тести й розвалювався перед справжніми пакетами — бо імпорт-заглушка це інструмент, що не працює. Переправлення в рідний хост — єдина форма, що може лишатися чесною до результатів.

### Плагіни DSH входять у pi: жива сесія DSH

Бандл DSH вимагає справжнього `ctx.tools`, справжнього `ctx.llm` і реєстру скілів, тож `dsh_install` просить живу сесію DSH самій завантажити бандл. Перешкода тут: бандл, встановлений керівником плагінів, це симлінк під `node_modules` профілю, і оголені специфікатори `@deepseek-ai/*` не резолвляться — замір дав `MODULE_NOT_FOUND`. Саме те виправляє `src/dsh-loader.js`: переписує такі специфікатори в URL модулів, які несе чинна збірка (справжні пакети, не заглушки); відносні імпорти, `node:` і сторонні лишаються як є. Бандл реєструється в хоста, а pi отримує переправний інструмент на кожну можливість.

Кінцева точка за замовчуванням закрита; звичайний запуск DSH не відчиняє жодного порту:

```bash
DSH_PI_BRIDGE_DSH_SERVE=43191 dsh ...                    # сторона DSH
DSH_PI_BRIDGE_DSH_ENDPOINT=127.0.0.1:43191 pi ...        # сторона pi
```

Прив'язка лише до 127.0.0.1; клієнт відкидає не-loopback-адреси. Коли живий DSH недосяжний, `dsh_install` чесно каже про це й відступає в режим перекладу, а не прикидається, що переправа вдалася.

### Коли жоден хост недосяжний

Мост усе одно розрішує джерело, компілює TypeScript (`stripTypeScriptTypes` із `node:module`, без підвантаження тулчейна) і фіксує, що пакет би зареєстрував, тому `preview` працює всюди. Реплікація реєстрацій в інший хост лишається для сценаріїв в одному хості та для бандлів, чий payload цілком дані — у бандла DSH, чистої теки скілів, немає викликного, але сам скіл проходить. Обидва хости реалізують [специфікацію Agent Skills](https://agentskills.io/specification).

### Форми параметрів і результатів

Інструменти DSH несуть таблицю властивостей (`{ text: { type: "string", required: true } }`), яку `@deepseek-ai/dsh-tools` компілює в JSON Schema; інструменти pi несуть JSON Schema напряму (TypeBox). `src/schema.js` конвертує в обидва боки, і результати проходять те саме проєктування: `{ content: [{ type: "text" }] }` pi та `{ ok, result }` DSH перекладаються одне в одного. Хост валідує схеми при реєстрації, і множина, яку приймає, вужча за чернетку JSON Schema — мітка `required` на вузлі властивості чи об'єктний масив `required` у схемі виходу валить активацію всього плагіна. Ці правила взято з замірів на встановлених хостах; тестовий набір несе їх як асерції.

## Перевірено — і як

Кожен пункт нижче мірявся проти справжніх хостів, а не проти підставок:

- Справжній запуск DSH, справжня модель, встановлення `npm:pi-web-access` і виклик через нього `web_web_search` (результати здобуває власний провайдер пакета)
- Справжня сесія DSH завантажує бандл з оголеним імпортом `@deepseek-ai/dsh-tools`, тоді окремий процес викликає його інструменти через loopback
- Цей мост виконує власний DSH-вхід тим самим механізмом, який чужий бандл зустрічає в pi

Кожен із них спіймав баг, недоступний підставі: файл, забутий опублікованим маніфестом; схему виходу, яку хост відкидає й через яку плагін тихо бездіє; `process.execPath`, що в процесі хоста вказує на застосунок, а не на node; нуль можливостей при перестворенні, бо демон уже завантажив пакет; скоуп, що забороняє присвоювання властивостей; server handler поза волокном, що підіймає сервіс; хост, який відкидає повторювані назви інструментів.

```bash
npm test                # усі офлайн-набори
npm run test:offline    # конвеєр + хост-входи обох сторін
npm run test:proxy      # демон, переправа на боці DSH і на боці pi
npm run test:host       # проти встановленої збірки DSH (див. примітку)
npm run test:network    # реально опубліковані пакети з npm і GitHub
npm run test:live       # те саме — проти реально робляючого pi
```

`test:host` читає власний `@deepseek-ai/dsh-tools` хоста зсередини asar встановленого хоста — це можливо лише через fs з патчем Electron; запускайте його всередині процесу хоста. Під звичайним node він прямо повідомляє SKIP, не натякаючи, що хост нам відмовив.

Офлайн-набори збирають фікстури руками — розширення pi мовою TypeScript на білдері TypeBox, бандл DSH на `defineTool`, бандл з оголеним імпортом пакета хоста — і женуть увесь конвеєр проти записаних підставок, а потім справді виконують інструменти, що вийшли з моста. Деякі правила живуть статичними асерціями, бо розкриваються лише при справжньому старті: форми схем, які приймає хост; файли, обов'язкові до публікації; те, що бандл, який аналізується, не має піднімати процеси й займати порти.

## Що не переходить

Мост чесно повідомляє такі випадки, а не тихо провалюється:

- **UI хоста**: браузерні сторінки DSH / `ctx.slots`; TUI-редер pi, `ctx.ui`, скорочення клавіш, прапорці CLI.
- **Адаптери моделей, що реєструються в хоста**: той, хто додає провайдера, робить це проти власного хоста — у цьому і смисл «не перекладати» — провайдери pi осідають у pi, адаптери DSH — у DSH.
- **Бандли DSH без викликного**: чистий оверлей інтерфейсу чи налаштувань не має інструментів для переправи. preview чесно це констатує, а не вигадує можливості.
- **Пакети, що вимагають інтерактивного хоста**: переправлений виклик може транслювати поступ, але не може показати вибір на іншій стороні.

## Постійність

Реєстрації негайно падають у теперішню сесію. Кожен хост при завантаженні плагіна перечитує з `~/.dsh-pi-bridge/bridges.json` те, що сам записав, тож установка переживає перезапуск — перевірено перезапуском сесії DSH з виявленням інструментів моста на місці. Перечитування читає лише кеш: старт хоста ніколи не чекає мережевого підвантаження; якщо кеш очищено, мост звітує про недоступність, замість виснути. Перезапуск робить нові інструменти видимими й іншим клієнтам (веб-GUI, друге вікно), бо ті складають перелік інструментів при старті. Вимикається налаштуванням `restoreOnLoad: false` у конфігурації бандла.

Ми не пишемо в налаштування жодного хоста. `bridge_remove` забуває міст і стирає його теку збірки; інструменти, уже зареєстровані в живому процесі, лишаються до перезапуску, бо мовчазна дерегістрація стану хоста гірша, ніж лишити їх видимими.

## Безпека

Мост-пакет **виконує код із вашими правами, на тому боці, де він працює**. Будь-який хост розширень висуває ту саму вимогу; цей пакет прийшов з іншої екосистеми і її маркетплейсового відбору не проходив, тож вимога тим більше. Спершу прочитайте його вихідний код; `preview` лише розбирає й оглядає, нічого не реєструючи.

Переправа — не пісочниця: пакет працює з повною довірою власного хоста, тому це і працює. Loopback-кінцева точка прив'язується лише до 127.0.0.1, відчиняється лише за заданого `DSH_PI_BRIDGE_DSH_SERVE`, а клієнт відкидає не-loopback-адреси. Той, хто дотягнеться до порту, зможе викликати будь-який інструмент, завантажений сесією. Відчиняйте порт лише тоді, коли потрібно.

## Устрій

```text
index.js                вхід DSH: name / inject / apply(ctx), тобто інструменти pi_*
extensions/index.js     вхід pi: фабрика default(pi), інструменти та команди dsh_*
skills/dsh-pi-bridge/   SKILL.md, спільний для обох хостів
cordis.patch.yml        монтування бандла DSH (ціль перемикача на панелі плагінів)
daemon/run.mjs          піднаглядний процес pi; loopback-фасад його інструментів
daemon/bootstrap.js     завантажується справжнім завантажувачем розширень pi всередину pi
src/proxy.js            сторона DSH: запустити/використати демона, переправляти виклики
src/dsh-loader.js       сторона DSH: завантажувати бандл у рантаймі проти живого scope
src/serve.js            сторона DSH: loopback-кінцева точка для іншого хоста
src/dsh-host-client.js  сторона pi: розмовляти з живою сесією DSH
src/resolve.js          джерела npm / git / url / локальні в кеш, з встановленням залежностей
src/load.js             побудова дзеркального дерева, компіляція TS, встановлення справжніх залежностей
src/manifest.js         впізнавання хоста за keywords, маніфестом і формою теки
src/capture.js          записані підставки-хости для обох вхідних конвенцій
src/schema.js           двобічне перетворення схем параметрів
src/capabilities.js     нормалізована модель можливостей; проєкція результатів
src/replay-dsh.js       capabilities -> ctx.tools / commands / skills
src/replay-pi.js        capabilities -> pi.registerTool / registerCommand
src/restore.js          перечитування записаних мостів при старті хоста
src/stubs.js            скан імпортів і творення заглушок для preview
src/tar.js              читач gzipped-tar, без залежностей
src/transpile.js        TypeScript -> ESM, через node:module
```

`index.js` імпортує лише вбудоване `node:` плюс власний пакет і оголошує `inject: ["tools"]` — єдиний потрібний йому сервіс. Скіли й налаштування досяжні через `ctx.inject` після перевірки можливостей; профіль без реєстру скілів просто не монтує скіл, замість падати на старті.
