# dsh-pi-bridge

یک پلاگین، دو میزبان. پس از نصب در pi، میزبان pi می‌تواند پلاگین‌های DeepSeek Harness را به کار بگیرد؛ پس از نصب در DSH، میزبان DSH می‌تواند پلاگین‌های pi را به کار بگیرد. هیچ‌یک از دو سو کد دیگری را با «ترجمه‌» اجرا نمی‌کند: پلاگین همیشه در میزبان بومی خودش اجرا می‌شود — جایی که API میزبان راستین است — و سوی دیگر فقط فراخوانی‌ها را عبور می‌دهد.

```text
# pi
pi install npm:dsh-pi-bridge            # یا: pi install git:github.com/Twofruitsgrape/dsh-pi-bridge

# DSH
dsh plugin --profile <name> install github:Twofruitsgrape/dsh-pi-bridge
```

پس از نصب، میزبان را دوباره راه‌اندازی کنید. هر دو کلیدواژه (`pi-package` و `dsh-plugin`) اعلان شده‌اند، بنابراین فروشگاه هر زیست‌بوم این بسته را می‌یابد.

## در هر میزبان چه چیز می‌گیرید

| | pi | DSH |
|---|---|---|
| به کار بستن پلاگین‌های سوی دیگر | `dsh_install`، `dsh_preview`، `/dsh-install`، `/dsh-preview` | `pi_install`، `pi_preview` |
| رشتنِ آنچه پُل شده | `/bridge-list`، `/bridge-remove` | `bridge_list`، `bridge_remove`، `bridge_status` |
| مهارت (skill) | `skills/dsh-pi-bridge/SKILL.md` | همان `SKILL.md`، سوارشده از راه دفتر مهارت‌ها |

هر دو سو دست‌ورز از همین قالب برای منابع است: `npm:<pkg>[@ver]`، `git:github.com/<owner>/<repo>[@ref]`، `github:<owner>/<repo>`، نشانی مخزن یا مسیر محلی — دقیقاً همان چیزهایی که هر میزبان از پیش می‌پذیرد.

قطعه‌ای از یک نشست واقعی، عین‌اللفظ: راه‌اندازی واقعی DSH، مدل واقعی، نصب یک بسته pi که واقعاً منتشر شده.

```text
dsh> pi_install({ source: "npm:pi-web-access", prefix: "web" })
  bridged npm:pi-web-access as pi-web-access@0.41.0
    mode: package code runs natively inside a supervised pi process
    tools: web_web_search, web_source_check, web_fetch_content,
           web_get_search_content, web_web_enable
    pi slash commands registered in pi: /websearch, /curator, /google-account, /search

dsh> web_web_search({ query: "DeepSeek V4" })   # ابزاری که از بسته pi آمده
  -> نتیجه‌های جست‌وجوی زنده، خوانده‌شده به دست provider خودِ بسته با پیکربندی خودش
```

## چگونه کار می‌کند

### پلاگین‌های pi که وارد DSH می‌شوند: فرایند pi زیرِ نگاه

`pi_install` بسته را در cache پُل عینیت می‌بخشد، وابستگی‌های واقعی‌اش را نصب می‌کند، و سپس آن را در فرایندی از pi (`pi --mode rpc`) که پُل نگاهش می‌کند بار می‌کند. هر بندی که pi گزارش کند، ابزاری در DSH می‌شود؛ فراخوانی‌ها به pi گذر می‌کنند و نتیجه‌ای که pi ساخته برمی‌گردد. پوشه `SKILL.md` صورتِ داده‌ای از راه `ctx.skills` سوار می‌شود. بسته، `registerTool` و `registerProvider` و دفتر الگوها و بادانش‌های provider راستین pi را می‌بیند — بسته‌ای که شبکه یا مدل را لمس کند، رفتارش با دستِ کاربر pi برابر برابر است.

این طرح، جایگزینِ آن رویکردِ پیشین است که ثبت‌ها را در DSH دوباره بازی می‌انداخت و بر importهای پوشیده با stub می‌اتکا می‌کرد. آن نسخه همه‌ی آزمون‌های نمونه‌وار را می‌گذراند و در برابر بسته‌های واقعی می‌پاشید — چون importی که stub خورده، ابزاری است که کار نمی‌کند. گذرِ فراخوانی به میزبان بومی، شکلِ یگانه‌ای است که می‌تواند نسبت به نتایج راستگو بماند.

### پلاگین‌های DSH که وارد pi می‌شوند: نشست DSH زنده

بسته‌ی بسته‌بندی‌شده‌ی DSH به `ctx.tools` و `ctx.llm` راستین و دفتر مهارت‌ها نیاز دارد؛ پس `dsh_install` از نشست زنده DSH می‌خواهد خودش بسته را بار کند. مانع همین‌جاست: بسته‌ای که مدیر پلاگین نصب کرده، پیوند نمادین است در زیر `node_modules` پروفایل، و شناسه‌های برهنه `@deepseek-ai/*` حل نمی‌شوند — آزمایش، `MODULE_NOT_FOUND` گزارش کرد. دقیقاً همین است کارِ `src/dsh-loader.js`: این شناسه‌ها را بازمی‌نویسد به نشانی‌های URL مدول‌هایی که ساختِ درحال اجرا همراه دارد (بسته‌های واقعی، نه stub)؛ درحالی‌که importهای نسبی، `node:` و importهای سوم به خودشان می‌مانند. بسته می‌رود نزد میزبان ثبت می‌شود، و pi برای هر توانایی یک ابزار منتقل‌شده می‌گیرد.

نقطه پایان به طور پیش‌فرض بسته است؛ راه‌اندازی معمولِ DSH هیچ درگاهی گشوده نمی‌کند:

```bash
DSH_PI_BRIDGE_DSH_SERVE=43191 dsh ...                    # سوی DSH
DSH_PI_BRIDGE_DSH_ENDPOINT=127.0.0.1:43191 pi ...        # سوی pi
```

فقط به 127.0.0.1 پیوسته می‌شود و مشتری نشانی‌های خارج از حلقه را پس می‌زند. هنگامی که نشست زنده‌ی DSH دست‌یافتنی نیست، `dsh_install` همین را راستگو می‌گوید و به حالت ترجمه برمی‌گردد، به‌جای آنکه بپنداردگذر موفق بوده.

### هنگامی که هیچ میزبانی در دست نیست

پُل همچنان سرچشمه را حل می‌کند، TypeScript را می‌سازد (`stripTypeScriptTypes` از `node:module`، بی‌آنکه toolchain دانلود شود)، و ضبط می‌کند که بسته چه ثبت خواهد کرد — پس `preview` هر جا کار می‌کند. احیاگری ثبت‌ها در میزبانی دیگر برای سناریوی همان میزبان و برای بسته‌هایی نگه داشته می‌شود که کل باریشان داده است — یک bundle از DSH با پوشهٔ skill صرف، هیچ چیز فراخوان‌کردنی ندارد، اما خود skill عبور می‌کند. هر دو میزبان، [قاعده‌ی Agent Skills](https://agentskills.io/specification) را پیاده‌سازی می‌کنند.

### شکل پارامترها و نتیجه‌ها

ابزارهای DSH جدول مشخصه‌های خواص را با خود می‌برند (`{ text: { type: "string", required: true } }`) که `@deepseek-ai/dsh-tools` آن را به JSON Schema می‌سازد؛ ابزارهای pi مستقیماً JSON Schema برمی‌دارند (TypeBox). `src/schema.js` در هر دو سو تبدیل می‌کند، و نتیجه‌ها هم همین تصویرشدن را می‌گذرانند: `{ content: [{ type: "text" }] }` از pi و `{ ok, result }` از DSH به هم ترجمه می‌شوند. میزبان هنگام ثبت، طرح‌ها را صحه می‌گذارد، و زیرمجموعه‌ای که می‌پذیرد از پیش‌نویس JSON Schema تنگ‌تر است — نشان `required` روی گره‌ی خاصه، یا آرایه `required` سطحِ شیء در طرح خروجی، رو_JOIN فعال‌سازی کل پلاگین را می‌اندازد. این قواعد از اندازه‌گیری روی میزبان‌های نصب‌شده آمده و مجموعه‌ی آزمون آن‌ها را به‌صورت ادعاهای ثابت دارد.

## بررسی‌شده — و چگونه

هر بند از فهرست زیر مقابلِ میزبانی واقعی سنجیده شد، نه مقابلِ نمونه‌های ساختگی:

- راه‌اندازی واقعی DSH، مدل واقعی، نصب `npm:pi-web-access` و فراخوانی `web_web_search` از راه آن (نتایج را provider خودِ بسته می‌آورد)
- نشست واقعی DSH بسته‌ای را با import برهنه‌ی `@deepseek-ai/dsh-tools` بار می‌کند، سپس فرایندی جداگانه ابزارهایش را از راه loopback صدا می‌کند
- این پُل ورودی DSH خودش را با همان سازوکاری اجرا می‌کند که بسته‌ی بیگانه‌ای در pi پیدا می‌کند

هر یک از آن‌ها باگی را گرفت که هیچ نمونه‌ی ساختگی نمی‌توانست: پرونده‌ای که بسته‌ی منتشرشده فراموش کرده بود؛ طرح خروجی که میزبان پس می‌راند و پلاگین بی‌صدا خاموش می‌ماند؛ `process.execPath` در فرایند میزبان به خود برنامه اشاره می‌کند نه به node؛ گزارش صفر توانایی هنگام نصب دوباره چون daemon بسته را از پیش بار کرده بود؛ scopeای که دادن مقدار به خاصه‌ها را نهی می‌کند؛ server handler بیرون از فیبر خدمت‌گذار؛ میزبانی که نام ابزار تکرارشده را می‌راند.

```bash
npm test                # همه‌ی مجموعه‌های تستِ بی‌شبکه
npm run test:offline    # خط لوله + ورودی‌های میزبانِ دو سو
npm run test:proxy      # daemon، انتقال‌ها از سو DSH و سو pi
npm run test:host       # مقابلِ ساختِ DSH نصب‌شده (یادداشت را ببینید)
npm run test:network    # بسته‌های منتشرشده‌ی واقعی از npm و GitHub
npm run test:live       # آزمون‌های بالا مقابلِ pi درحال اجرای واقعی
```

`test:host` از درون asarِ میزبانِ نصب‌شده می‌خواند — مقابلِ `@deepseek-ai/dsh-tools` خود میزبان — چیزی که فقط با fs وصله‌دارِ Electron ممکن است؛ پس آن را درون فرایند میزبان اجرا کنید. با node معمولی، SKIP را بی‌ابهام گزارش می‌کند، بدون آنکه تلمیح دهد میزبان ما را پس زده.

مجموعه‌های بی‌شبکه وسائل آزمون را با دست می‌سازند — پسوندی pi به زبان TypeScript با سازنده‌ی TypeBox، bundleی از DSH با `defineTool`، و bundleای با import برهنه‌ی بسته‌ی میزبان — سپس خط لوله‌ی کامل را مقابلِ stubهای ضبط‌شده می‌رانند و ابزارهایی که از پُل بیرون آمده را واقعاً اجرا می‌کنند. برخی قواعد به شکل ادعای ایستا زندگی می‌کنند، چون فقط در آغازِ راستین خودشان را نشان می‌دهند: شکل طرح‌هایی که میزبان می‌پذیرد؛ پرونده‌هایی که باید منتشر شوند؛ و اینکه bundle درحال تحلیل نباید فرایندی بیفرازد یا درگاهی بگیرد.

## چه چیزهایی عبور نمی‌کنند

پُل این موارد را صادقانه اعلام می‌کند:

- **رابط کاربری میزبان**: صفحات مرورگرِ DSH / `ctx.slots`؛ رندربة TUI و `ctx.ui` و کلیدهای میان‌بر و فلگ‌های CLI.
- **مبدل‌های مدلِ ثبت‌شده پیش میزبان**: هر کس provider می‌افزاید، آن را با میزبان خویش انجام می‌دهد — همین است معنیِ «ترجمه‌نکردن» — providerهای pi در pi می‌افتند و adapterهای DSH در DSH می‌افتند.
- **bundleهای DSH با هیچ فراخوان‌کردنی**: لایه‌ای که صرفاً رابط یا صرفاً تنظیمات باشد، هیچ ابزاری برای انتقال ندارد. preview همین را صریح می‌گوید، به‌جای آنکه توانایی‌ها را جعل کند.
- **بسته‌هایی که به میزبان تعاملی نیاز دارند**: فراخوانیِ منتقل‌شده می‌تواند پیشرفت را به‌صورت جریان بفرستد، اما نمی‌تواند در سوی دیگر یک گزینگر باز کند.

## پایایی

ثبت‌ها بلافاصله در نشست جاری می‌نشینند. هر میزبان هنگام بارگیری پلاگین از `~/.dsh-pi-bridge/bridges.json` آنچه را که خود ثبت کرده دوباره می‌خواند؛ بنابراین نصب، از بازراه‌اندازی می‌گذرد — آزم‌شده با بازراه‌اندازی نشست DSH و یافتن ابزارهای پُل در جایگاهشان. بازخوانی فقط cache را می‌خواند: راه‌اندازی میزبان هرگز دانلود شبکه را انتظار نمی‌کشد؛ اگر cache پاک شده باشد، پُل دست‌نامرسانِ غیرپذیر را اعلام می‌کند، نه معطلی. بازراه‌اندازی همچنین ابزارهای تازه را برای مشتری‌های دیگر (GUI وب، پنجره دوم) نیز نمایان می‌کند، چون آن‌ها در آغاز، فهرست ابزارها را می‌سازند. با `restoreOnLoad: false` در پیکربندی bundle خاموش‌شدنی است.

در تنظیمات هیچ میزبان نمی‌نویسیم. `bridge_remove` یک پُل را از یاد می‌برد و پوشه build آن را حذف می‌کند؛ ابزارهای ثبت‌شده در فرایند زنده تا بازراه‌اندازی می‌مانند، چون لغو ثبتِ بی‌صدا در وضع میزبان بدتر از دیدنی‌ماندن است.

## امنیت

بسته پیوندی **کد را با اجازه‌های شما می‌اجرا می‌کند، در میزبانی که آن را اجرا شود.** هر میزبانِ افزودنی همین مطالبه را دارد؛ این بسته از زیست‌بومی دیگر آمده و از بازبینیِ فروشگاهِ آن نگذشته است، پس مطالبه سخت‌تر است. اول سورسش را بخوانید؛ `preview` فقط تحلیل و بازبینی می‌کند و هیچ‌چیز ثبت نمی‌کند.

فراخوانیِ منتقل‌شده sandbox نیست: بسته با اعتماد کامل میزبان خودش اجرا می‌شود — دلیل کارکرد همین است. پایگاه loopback فقط به 127.0.0.1 پیوسته می‌شود؛ فقط وقتی `DSH_PI_BRIDGE_DSH_SERVE` تنظیم شده باشد باز می‌شود؛ و مشتری نشانی‌های غیر حلقه را پس می‌زند. هر کسی که به آن در برسد، هر ابزاری که نشست بار کرده می‌تواند صدا کند. پس باز نکنید، مگر ضرورت داشته باشد.

## طرح

```text
index.js                ورودی DSH: name / inject / apply(ctx)، یعنی ابزارهای pi_*
extensions/index.js     ورودی pi: کارخانه default(pi)، ابزارها و فرمان‌های dsh_*
skills/dsh-pi-bridge/   SKILL.md، مشترک میان هر دو میزبان
cordis.patch.yml        سوارسازی bundle DSH (هدف کلیدِ پنل افزونه‌ها)
daemon/run.mjs          فرایند pi زیرِ نگاه؛ پیشانی loopback ابزارهایش
daemon/bootstrap.js     با بارکنندِ واقعی افزونه‌های pi، درون pi بار می‌شود
src/proxy.js            سو DSH: بازراه‌اندازی/بازاستفاده از daemon، منتقل‌کردن فراخوانی‌ها
src/dsh-loader.js       سو DSH: بارگذاری bundle در زمان اجرا، در برابر scope زنده
src/serve.js            سو DSH: نقطه پایان loopback برای میزبان دیگر
src/dsh-host-client.js  سو pi: گفت‌وگو با نشست زنده DSH
src/resolve.js          منبع‌های npm / git / url / محلی به cache، همراه نصب پس‌نیازها
src/load.js             ساخت درخت آینه‌ای، سازی TS، نصب پس‌نیازهای واقعی
src/manifest.js         شناسایی میزبان از کلیدواژه‌ها، بسته‌بان، و شکل پوشه
src/capture.js          میزبان‌های stub ثبت‌شده، برای دو قرارداد ورودی
src/schema.js           تبدیل دوطرفه‌ی طرح پارامترها
src/capabilities.js    مدل توانایی استانداردشده؛ تصویر نتیجه‌ها
src/replay-dsh.js       capabilities -> ctx.tools / commands / skills
src/replay-pi.js        capabilities -> pi.registerTool / registerCommand
src/restore.js          بازخوانی پل‌های ثبت‌شده در آغاز میزبان
src/stubs.js           اسکنِ importها و ساختِ stub برای preview
src/tar.js              خواننده gzipped-tar، بی پس‌نیاز
src/transpile.js        TypeScript -> ESM، از راه node:module
```

`index.js` فقط builtin هاي `node:` را به‌علاوه خود بسته می‌آورد و `inject: ["tools"]` را اعلام می‌کند — تنها خدمتی که نیاز دارد. مهارت‌ها و تنظیمات پس از گ.Primaryهاکن نی، از راه `ctx.inject` در دست‌رس‌اند؛ پروفایلی بی‌دفتر مهارت، فقط مهارت را نمی‌سازد و آغاز را نمی‌اندازد.
