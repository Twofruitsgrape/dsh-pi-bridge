# dsh-pi-bridge

ปลั๊กอินเดียว โฮสต์สองตัว ติดตั้งลงใน pi แล้ว pi จะใช้ปลั๊กอินของ DeepSeek Harness ได้ ติดตั้งลงใน DSH แล้ว DSH จะใช้ปลั๊กอินของ pi ได้ ไม่มีฝ่ายใด "แปลรหัส" ของอีกฝ่ายเพื่อทำให้มันทำงาน: ปลั๊กอินทำงานอยู่เสมอในโฮสต์บ้านเกิดของมันเอง — ซึ่ง API ของโฮสต์ที่นั่นของแท้ — ส่วนอีกฝ่ายทำได้แค่ส่งต่อการเรียกใช้

```text
# pi
pi install npm:dsh-pi-bridge            # หรือ: pi install git:github.com/Twofruitsgrape/dsh-pi-bridge

# DSH
dsh plugin --profile <name> install github:Twofruitsgrape/dsh-pi-bridge
```

หลังติดตั้งให้รีสตาร์ทโฮสต์ คีย์เวิร์ดทั้งสอง (`pi-package` และ `dsh-plugin`) ได้ประกาศไว้แล้ว ตลาดของแต่ละระบบนิเวศจึงค้นพบแพ็กเกจนี้ได้

## คุณได้อะไรในแต่ละโฮสต์

| | pi | DSH |
|---|---|---|
| ใช้ปลั๊กอินของอีกฝ่าย | `dsh_install`, `dsh_preview`, `/dsh-install`, `/dsh-preview` | `pi_install`, `pi_preview` |
| จัดการสิ่งที่เชื่อมข้ามไว้ | `/bridge-list`, `/bridge-remove` | `bridge_list`, `bridge_remove`, `bridge_status` |
| Skill | `skills/dsh-pi-bridge/SKILL.md` | `SKILL.md` ไฟล์เดียวกัน เสียบผ่านทะเบียน skill |

ทั้งสองฝ่ายใช้ไวยากรณ์ต้นทางชุดเดียวกัน: `npm:<pkg>[@ver]`, `git:github.com/<owner>/<repo>[@ref]`, `github:<owner>/<repo>`, URL ของรีโพ หรือพาธในเครื่อง — ตรงกับฟอร์แมตที่โฮสต์แต่ละตัวยอมรับอยู่แล้ว

ตัวอย่างตอนหนึ่งของเซสชันจริง บันทึกตามคำพูดเป๊ะ ๆ: การสตาร์ท DSH ของจริง โมเดลของจริง การติดตั้งแพ็กเกจ pi ที่เผยแพร่จริง

```text
dsh> pi_install({ source: "npm:pi-web-access", prefix: "web" })
  bridged npm:pi-web-access as pi-web-access@0.41.0
    mode: package code runs natively inside a supervised pi process
    tools: web_web_search, web_source_check, web_fetch_content,
           web_get_search_content, web_web_enable
    pi slash commands registered in pi: /websearch, /curator, /google-account, /search

dsh> web_web_search({ query: "DeepSeek V4" })   # เครื่องมือที่มาจากแพ็กเกจ pi
  -> ผลค้นหาแบบสด ๆ ดึงโดย provider ของแพ็กเกจเองด้วยการตั้งค่าของมัน
```

## ทำงานอย่างไร

### ปลั๊กอินของ pi ไหลเข้าสู่ DSH: กระบวนการ pi ที่มีคนเฝ้าดู

`pi_install` แม่แปลงแพ็กเกจลงแคชของสะพาน ติดตั้ง dependencies จริงของมัน แล้วโหลดมันภายในกระบวนการ pi (`pi --mode rpc`) ที่สะพานคอยเฝ้าดู ทุกรายการที่ pi รายงานกลายเป็นเครื่องมือหนึ่งชิ้นใน DSH การเรียกใช้ถูกส่งต่อไปยัง pi และคืนผลลัพธ์ที่ pi คำนวณได้ ไดเรกทอรี `SKILL.md` ถูกเสียบเป็นข้อมูลผ่าน `ctx.skills` ที่แพ็กเกจมองเห็นคือ `registerTool`, `registerProvider`, ทะเบียนโมเดล และข้อมูลรับรอง provider ของ pi ของแท้ — แพ็กเกจที่แตะเน็ตหรือโมเดลจะทำตัวเหมือนอยู่ในมือผู้ใช้ pi ทุกประการ

การออกแบบนี้แทนที่แนวทางเดิมที่รีเพลย์รายการลงใน DSH แล้วพึ่ง import ที่ถูกใส่ stub ไว้ ฉบับนั้นผ่านบททดสอบมอกทั้งหมด แต่พังทลายเมื่อเจอแพ็กเกจจริง — เพราะ import ที่ stub ไว้นั้นคือเครื่องมือที่ใช้ไม่ได้ การส่งต่อเข้าโฮสต์แท้คือรูปแบบเดียวที่ยังซื่อสัตย์ต่อผลลัพธ์ได้

### ปลั๊กอินของ DSH ไหลเข้าสู่ pi: เซสชัน DSH ที่ยังมีชีวิต

bundle ของ DSHต้องการ `ctx.tools`, `ctx.llm` ของจริง และทะเบียน skill ดังนั้น `dsh_install` ร้องขอให้เซสชัน DSH ที่ยังมีชีวิตโหลด bundle เอง อุปสรรคอยู่ตรงนี้: bundle ที่ตัวจัดการปลั๊กอินติดตั้งเป็น symlink อยู่ใต้ `node_modules` ของโปรไฟล์ และตัวระบุเปล่า ๆ `@deepseek-ai/*` หาเจอไม่ได้ — การวัดได้รายงาน `MODULE_NOT_FOUND` นี่เองที่ `src/dsh-loader.js` ทำงาน: มันเขียนใหม่ให้ตัวระบุพวกนี้เป็น URL ของโมดูลที่บิลด์ที่กำลังทำงานนำพามา (แพ็กเกจของจริง ไม่ใช่ stub) import เชิงสัมพัทธ์, `node:` และ import ของบุคคลที่สามคงเดิม บันเดิลไปลงทะเบียนกับโฮสต์ และ pi ได้รับเครื่องมือส่งต่อหนึ่งชิ้นต่อหนึ่ง capability

ปลายทางปิดอยู่เป็นค่าเริ่มต้น การสตาร์ท DSH ปกติไม่เปิดพอร์ตใด ๆ:

```bash
DSH_PI_BRIDGE_DSH_SERVE=43191 dsh ...                    # ฝั่ง DSH
DSH_PI_BRIDGE_DSH_ENDPOINT=127.0.0.1:43191 pi ...        # ฝั่ง pi
```

ผูกกับ 127.0.0.1 เท่านั้น และลูกข่ายปฏิเสธที่อยู่ที่ไม่ใช่ loopback เมื่อถึง DSH ที่มีชีวิตไม่ได้ `dsh_install` จะบอกความจริงตรง ๆ แล้วย้อนกลับสู่โหมดแปลภาษา แทนที่จะแสร้งว่าส่งต่อสำเร็จ

### เมื่อโฮสต์ทั้งสองเข้าไม่ถึง

สะพานยังคงแกะแหล่งที่มา คอมไพล์ TypeScript (`stripTypeScriptTypes` ของ `node:module` ไม่ต้องดาวน์โหลด toolchain) และจับว่าแพ็กเกจจะลงทะเบียนอะไร ดังนั้น `preview` ใช้ได้ทุกที่ การรีเพลย์รายการไปยังโฮสต์อีกฝ่ายถูกสงวนไว้สำหรับสถานการณ์โฮสต์เดียวกัน และสำหรับบันเดิลที่เพย์โหลดทั้งหมดคือข้อมูล — bundle ของ DSH ที่เป็นแค่ไดเรกทอรี skill ล้วนไม่มีอะไรให้เรียก แต่ตัว skill เองผ่านไปได้ ทั้งสองโฮสต์ต่างใช้[ข้อกำหนด Agent Skills](https://agentskills.io/specification)

### รูปร่างของพารามิเตอร์และผลลัพธ์

เครื่องมือของ DSH แบกตารางสเปคของพร็อพเพอร์ตี้ (`{ text: { type: "string", required: true } }`) ที่ `@deepseek-ai/dsh-tools` คอมไพล์เป็น JSON Schema เครื่องมือของ pi แบก JSON Schema ตรง ๆ (TypeBox) `src/schema.js` แปลงสองทาง และผลลัพธ์ก็ผ่านการฉายแบบเดียวกัน: `{ content: [{ type: "text" }] }` ของ pi กับ `{ ok, result }` ของ DSH แปลงกันได้ โฮสต์พิสูจน์สคีมาตอนลงทะเบียน และชุดย่อยที่ยอมรับแคบกว่าฉบับร่างของ JSON Schema — เครื่องหมาย `required` บนโหนดพร็อพเพอร์ตี้ หรืออาร์เรย์ `required` ระดับโอบเจ็กต์ในสคีมาผลลัพธ์ ทำให้การเปิดใช้งานปลั๊กอินทั้งตัวล้มเหลว กฎเหล่านี้มาจากการวัดกับโฮสต์ที่ติดตั้งแล้ว ชุดทดสอบบันทึกมันเป็นบทยืนยัน

## พิสูจน์แล้ว — และพิสูจน์อย่างไร

ทุกข้อต่อไปนี้ถูกวัดกับโฮสต์ของจริง ไม่ใช่กับมอก:

- สตาร์ท DSH ของจริง โมเดลของจริง ติดตั้ง `npm:pi-web-access` แล้วเรียก `web_web_search` ผ่านมัน (ผลลัพธ์ได้จาก provider ของแพ็กเกจเอง)
- เซสชัน DSH จริงโหลดบันเดิลที่ import แบบเปล่า ๆ `@deepseek-ai/dsh-tools` แล้วโปรเซสแยกต่างหากเรียกเครื่องมือของมันผ่าน loopback
- สะพานนี้รันทางเข้า DSH ของตัวเองด้วยกลไกเดียวกันที่บันเดิลแปลกถิ่นต้องเจอใน pi

ทุกข้อข้างบนจับได้บั๊กที่มอกจับไม่ได้เลย: ไฟล์ที่แมนิเฟสต์ที่เผยแพร่ลืม สคีมาผลลัพธ์ที่โฮสต์ปฏิเสธทำให้ปลั๊กอินหยุดนิ่งเงียบ ๆ เงียบ ๆ; `process.execPath` ในกระบวนการโฮสต์ชี้ไปที่แอปไม่ใช่ node; การรายงานศูนย์ความสามารถเวลาติดตั้งซ้ำเพราะเดมอนโหลดแพ็กเกจไว้ก่อนแล้ว; สโคปที่ห้ามกำหนดค่าพร็อพเพอร์ตี้; server handler ที่วิ่งนอกไฟเบอร์ที่ตื่นบริการ; โฮสต์ที่ปฏิเสธชื่อเครื่องมือซ้ำ

```bash
npm test                # ชุดออฟไลน์ทั้งหมด
npm run test:offline    # สายการผลิต + ทางเข้าโฮสต์ของทั้งสองฝั่ง
npm run test:proxy      # เดมอน, การส่งต่อฝั่ง DSH และฝั่ง pi
npm run test:host       # กับบิลด์ DSH ที่ติดตั้งแล้ว (ดูหมายเหตุ)
npm run test:network    # แพ็กเกจเผยแพร่จริงจาก npm และ GitHub
npm run test:live       # บททดสอบข้างบนเทียบกับ pi ที่กำลังรันจริง
```

`test:host` อ่าน `@deepseek-ai/dsh-tools` ของโฮสต์เองจากข้างใน asar ของโฮสต์ที่ติดตั้ง — มีแต่ fs ที่ปะ Electron เท่านั้นที่อ่านได้ รันมันภายในกระบวนการโฮสต์เถิด กับ node ปกติมันรายงาน SKIP อย่างชัดเจน ไม่ยกนิ้วชี้ว่าโฮสต์ปฏิเสธพวกเรา

ชุดออฟไลน์ปั้นฟิกซ์เจอร์ขึ้นด้วยมือ — ส่วนขยาย pi เขียนด้วย TypeScript ใช้บิลเดอร์ TypeBox, bundle ของ DSH ใช้ `defineTool`, บันเดิลที่ import แพ็กเกจโฮสต์แบบเปล่า ๆ — แล้วสั่งทั้งสายการผลิตวิ่งกับสตับที่บันทึกไว้ และรันเครื่องมือที่ไหลออกจากสะพานอย่างแท้จริง กฎบางข้ออยู่ในรูปบทยืนยันแบบสถิต เพราะมันเอวังตัวเองเมื่อสตาร์ทจริงเท่านั้น: รูปร่างสคีมาที่โฮสต์ยอมรับ ไฟล์ที่ต้องเผยแพร่ ความจริงที่ว่าบันเดิลที่กำลังถูกวิเคราะห์ห้ามตื่นโปรเซสหรือผูกพอร์ต

## อะไรไม่ข้ามไป

สะพานรายงานกรณีเหล่านี้อย่างตรงไปตรงมา ไม่ใช่ล้มเงียบ ๆ:

- **UI ของโฮสต์**: หน้าเบราว์เซอร์ของ DSH / `ctx.slots` เรนเดอเรอร์ TUI ของ pi, `ctx.ui`, คีย์ลัด, แฟล็ก CLI
- **อะแดปเตอร์โมเดลที่ลงทะเบียนกับโฮสต์**: ผู้เพิ่ม provider ทำมันกับโฮสต์บ้านเกิดของตัวเอง — นี่คือนัยของ "ไม่แปล" — provider ของ pi ตกลงใน pi, adapter ของ DSH ตกลงใน DSH
- **บันเดิล DSH ที่ไม่มีอะไรให้เรียก**: โอเวอร์เลย์ที่เป็นแค่หน้าตาหรือแค่การตั้งค่าไม่มีเครื่องมือให้ส่งต่อ preview พูดชัด ๆ แบบนั้น ไม่ใช่ปั้นความสามารถขึ้นมา
- **แพ็กเกจที่ต้องการโฮสต์แบบโต้ตอบ**: การเรียกที่ส่งต่อส่งความคืบหน้าเป็นสตรีมได้ แต่ดันเปิดตัวเลือกที่อีกฝั่งไม่ได้

## ความต่อเนื่อง

รายการลงทะเบียนร่วงลงเซสชันปัจจุบันทันที แต่ละโฮสต์ที่จุดโหลดปลั๊กอินจะอ่านซ้ำจาก `~/.dsh-pi-bridge/bridges.json` สิ่งที่ตัวเองเคยจดไว้ การติดตั้งจึงรอดการรีสตาร์ท — ทดสอบแล้วด้วยการรีสตาร์ทเซสชัน DSH แล้วพบเครื่องมือของสะพานอยู่ครบ การอ่านซ้ำอ่านแคชอย่างเดียว: การสตาร์ทโฮสต์ไม่เคยรอการดาวน์โหลดเครือข่าย เมื่อแคชถูกล้างสะพานรายงานว่าใช้ไม่ได้ ไม่ใช่ค้างแช่แข็ง การรีสตาร์ทยังทำให้เครื่องมือใหม่เห็นได้กับลูกค้าตัวอื่น (เว็บ GUI, หน้าต่างที่สอง) เพราะพวกมันประกอบรายการเครื่องมือตอนสตาร์ท ปิดได้ด้วย `restoreOnLoad: false` ในการตั้งค่าบันเดิล

เราไม่เขียนลงการตั้งค่าของโฮสต์ใดทั้งสิ้น `bridge_remove` ลืมสะพานหนึ่งแห่งและลบไดเรกทอรีบิลด์มันทิ้ง เครื่องมือที่ลงทะเบียนกับโปรเซสที่กำลังวิ่งอยู่จนเวลาแล้วจนเล่าจะรอจนรีสตาร์ท เพราะการยกเลิกลงทะเบียนสถานะโฮสต์แบบเงียบ ๆ มันแล้วว่ายังให้มันเห็นอยู่นั่นเลย

## ความปลอดภัย

แพ็กเกจที่ถูกเชื่อมข้าม **รันโค้ดด้วยสิทธิ์ของคุณ บนโฮสต์ตรงที่มันทำงาน** โฮสต์ส่วนขยายทุกตัวตั้งข้อเรียกร้องเดียวกัน แพ็กเกจนี้มาจากระบบนิเวศข้างฝั่งและไม่ผ่านการตรวจของตลาดนั้น ข้อเรียกร้องจึงหนักขึ้นอีก อ่านซอร์สโค้ดของมันก่อน `preview` แค่แกะและส่องดู ไม่ลงทะเบียนอะไรทั้งนั้น

การส่งต่อไม่ใช่แซนด์บ็อกซ์: แพ็กเกจวิ่งด้วยความไว้วางใจเต็มล้นของโฮสต์ตัวเอง นี่คือเหตุผลที่มันทำงานได้ ปลายทาง loopback ผูก 127.0.0.1 อย่างเดียว เปิดก็ต่อเมื่อ `DSH_PI_BRIDGE_DSH_SERVE` ถูกกำหนด และลูกข่ายปฏิเสธที่อยู่ที่ไม่ใช่ loopback ใครก็ตามที่แตะพอร์ตนั้นได้จะเรียกเครื่องมือที่เซสชันโหลดไว้ได้ทั้งหมด ไม่จำเป็นก็อย่าเปิด

`index.js` import แค่ builtin ของ `node:` บวกแพ็กเกจของตัวเอง แล้วปফระดับ `inject: ["tools"]` บริการเดียวที่ต้องการ skill และการตั้งค่าแตะถึงได้ผ่าน `ctx.inject` หลังผ่านการตรวจความสามารถ โปรไฟล์ที่ไม่มีทะเบียน skill ก็เสียบ skill ไม่ลงเท่านั้น ไม่ได้ทำให้การสตาร์ทล้ม
